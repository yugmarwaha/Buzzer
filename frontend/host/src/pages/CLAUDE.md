# pages

## Purpose
Top-level routed screens for the Host app: signing in, picking a course/quiz to host, and running a live game session end to end.

## Contents
- CoursesPage.tsx — post-login landing page: the host's courses (`/game/my-courses`) and their own open rooms, each with a Manage link to that course's Rooms tab (where Rejoin/End live). `/home` redirects here.
- course/CourseLayout.tsx — header + Quizzes / Rooms / Roster / Sessions / Images tabs for one course (five columns; labels shrink to `text-xs` below 400px so they fit a phone).
- course/ImagesPage.tsx — T8 Images tab (`/courses/:courseId/images`): the course's current images with size, dimensions and usage (`use_count` + archived); Upload, Replace (new version, repoints non-archived quizzes) and Delete (the server's 409 names the quizzes that still use it); files over 5 MB are refused before uploading.
- course/QuizzesPage.tsx — create, import, export, archive/restore, start room; no delete.
- course/RoomsPage.tsx — every LOBBY/IN_PROGRESS room in the course (MySQL-driven, with `answered_count`; stale ones say "Not running"); End room only where `can_end`. The list also refreshes itself every 5 seconds while the tab is visible (no loading flash; a failed refresh keeps the old list; the Refresh button stays). A successful manual load or refresh clears the error.
- course/RosterPage.tsx — moved from admin: CSV import wizard (parsed client-side) + inline table.
- course/SessionsPage.tsx — finished sessions (any host's): CSV/HTML downloads, guest merge where `can_merge_guests`; with 3 or more sessions and different player counts, a titled `charts/Sparkline` shows players per session, oldest to newest.
- QuestionEditorPage.tsx — moved from admin; token-styled like the rest (lucide icons, no raw palette classes); read-only while `has_active_room` or archived; delete disabled for answered questions. One `QuestionForm` serves add and edit: `questionToForm` unpacks a question's `config`/`answer_data` into flat per-type form fields, `formToPayload` packs them back, and both add (`POST`) and edit (`PUT`) send the full payload to `/host/games/{id}/questions[/{qid}]`. T7 types: Pin Drop target from two −5..5 `<select>`s with a `PinGrid` preview; Closest Guess correct/tolerance/unit fields kept as text; `newTypeProblem` mirrors the server rules (prompt, numbers ≤ 1e12, 0 ≤ F ≤ P, unit ≤ 20 code points, points > 0 under ACCURACY) and disables Save with an inline message. Every type now needs a prompt before Save ("Enter the question prompt"), and `formProblem` mirrors the shared `QuestionCreate` rules (time limit a whole number 2–300, multi-select at least 2 kept options, MC/FITB points 0 or more, FITB ACCURACY at least one non-blank answer and a whole-number edit distance, computed points 0–100000). T8: `ImagePicker`s for the question image (all types) and the Pin Drop background, and a per-option image button in `AnswerRows` (multiple choice and multi-select). Each option row carries its own `imageId` and a client-only `rowId`; `AnswerRows` passes updaters, and an image chosen after an upload is set by `rowId`, so edits made during the upload are kept. Adding, removing or reordering options moves the image with it; `formToPayload` sends `optionImageIds` aligned with `options` (omitted when all empty) and keeps an empty multi-select option that has an image. `imageProblem` blocks Save with "Option B needs text or an image". The list view shows prompt/option images and an "older image version" note.
- LoginPage.tsx — sign-in screen (the `ThemeToggle` is top-right via `App.tsx`); primary path is UW NetID OAuth2 redirect (parses a `temp_token` out of the URL hash on return and exchanges it for an access token), secondary path is username/password against `/auth/login`.
- game/GameLayout.tsx — layout + data layer for an in-progress room. Opens the Socket.IO connection (`join_room` as `HOST`), owns all game state (phase, players, current question, results, game-over) in a `GameContext`, and renders `<Outlet/>` plus an **End game** button (top-right, outline danger) and a QR/room-code glass panel that is hidden on the lobby route (the lobby already shows a large QR and room code) and on game over (no one joins then). The `<Outlet/>` keeps the full page width, so each page centers itself with its own `max-w-*` and `mx-auto`. The wrapper has `pt-14` so the fixed theme toggle and End game never overlap a page header on short windows. The pages below it fill the wrapper with `flex-1` (not `min-h-screen`), so the padding does not make the page scroll. The panel is a fixed bottom-right tile from 1480px wide (the gutter beside the widest page, `max-w-6xl`, has room for it); below that it sits in a centered row under the content, so it never covers the page. Also drives navigation between the other game/ pages based on socket events.
- game/LobbyPage.tsx — pre-game screen: a glass join panel (QR tile + `text-code` room code + join URL), live player count (pops on change), auto-advance toggle (`role="switch"`), Start Game button (`xl`).
- game/QuestionPage.tsx — shows the active question's prompt and type label (not its options; for `pin_drop` an empty `PinGrid`, for `closest_guess` the unit — both hidden while locked, like the prompt), a countdown (`TimerBar`), answered-count, and Lock/Show Results controls; auto-advances after `answerPhaseEnded` when auto-advance is on. Classroom-readable: type and grading are `Badge`s, the prompt is `text-stage` in a `Card variant="question"` with a `max-h-[45vh] overflow-y-auto` scroll container (`py-1` keeps the glyphs of a prompt that fits inside the box, so no scrollbar shows; `text-pretty`, not `text-balance`), and the answered count is a `text-stat` number (ticks on change) over a `Progress` bar. T8: with a question image the prompt steps down to `text-title` and the image (eager, up to 42vh) sits under it in the card, so the whole screen still fits a projector; the Pin Drop grid draws its background.
- game/ResultsPage.tsx — per-question results: `charts/AnswerBars` (size `lg`; option labels wrap, the correct option gets a check and the word "Correct") beside a `charts/DonutStat` response rate for multiple_choice/true_false/multi_select, or a client-computed word cloud for fill_in_the_blank (words within the edit distance of an accepted answer are `text-success`, computed with Levenshtein), or `components/NewTypeResults` for the T7 types; auto-advances on a countdown when enabled.
- game/GameOverPage.tsx — final screen: avg/high/player-count stat cards, a `charts/ScoreHistogram` (auto-bucketed), a `charts/QuestionAccuracyChart` overview, and a per-question `QuestionCard` list (`charts/AnswerBars` size `md` plus a `charts/DonutStat`; T7 types use `NewTypeResults`, whose closest_guess view is a `charts/BandBar`). It builds its own bar rows (see Gotchas — not shared with ResultsPage). The server's `scores` list only has players with a score row, so the page pads it with 0s up to `playerCount` (a player who never answered still counts in the average and histogram).

## Styling
All pages use the shared token classes (`bg-surface`, `text-primary`, `border-line`, `bg-accent`, `text-success`/`text-danger`/`text-warning`, etc.), lucide-react icons instead of decorative emoji, and the `components/ui` `Button`/`Input`/`Card`. Host room-facing text on `game/*` is large for a projector. Rules and rationale: `frontend/CLAUDE.md` and `docs/plans/ui-themes.md` (section 3.8).

## How it fits in
These are the route targets mounted by the app's router (frontend/host/src). Most pages import UI primitives from `components/ui` and the fetch helper from `lib/api`, but not uniformly: `game/GameLayout.tsx` uses `components/ui/button` (End game, error screen) plus `QRCodeSVG`, and calls `lib/api` for the room-title fetch; `LobbyPage`/`QuestionPage`/`ResultsPage`/`GameOverPage` never call `lib/api` directly — they read everything through `useGame()` from GameLayout instead.

## Gotchas
- **One socket per game:** GameLayout's socket effect depends only on `code`; `navigate` is held in `navigateRef` and every handler calls `navigateRef.current(...)`. Putting `navigate` (or anything that changes per route) back into the dependency array would reconnect on every in-game navigation, which the server treats as a host disconnect (auto-lock, "host disconnected", auto-unlock).
- **QR panel rule:** the corner join/QR panel is skipped when the pathname ends in `/lobby` or `/gameover`; `LobbyPage` shows its own larger QR. Both QR wrappers are `bg-white` marked `theme-exempt` (QR must stay black on white); don't swap them for tokens.
- **Theme toggle on `/game/*`** is top-left (App.tsx `ThemeCorner`) because End game is top-right; keep new fixed controls off both top corners.
- **Don't add raw palette classes** (`text-red-500`, `bg-gray-800`, `text-accent`, text opacity modifiers, classes built from string fragments) in any page; `npm run check:colors` flags them.
- All game/ pages assume they render under `GameLayout`'s `<Outlet/>` — `useGame()` throws if called outside that context.
- GameLayout treats a failed `/game/rooms/:code` fetch (title + session id) as non-fatal. Socket `connect_error`/`error` events are fatal (a full error screen with a way back to `/courses`, cleared on `connect`) only before the socket has joined (first `sync_state`; reset on `disconnect`). After that they, and a failed End game, show a dismissible top-center notice (`role="alert"`) and the game keeps running. Its **End game** button (hidden on game over) calls `POST /host/sessions/{id}/end`; on success (or 404/409, already ended) it navigates to `/courses` itself; the `game_abandoned` event does the same when the room is ended elsewhere.
- QuestionPage hides the question prompt entirely while the question is locked — only the timer/counts/buttons remain visible (locking also pauses the `TimerBar`).
- `answer_phase_ended` socket events are filtered by `questionId` in GameLayout to ignore stale events from a previous question's orphaned timer task — a reader relying on phase transitions should be aware stale events are possible.
- GameLayout's `sync_state` handler mirrors the server's lock flag both ways (`setQuestionLocked(!!data.questionLocked)`, and `lockedTimerSeconds` from `timerRemainingSeconds` only while locked) so a stale local lock can't survive a resync. It also restores `answeredCount`/`allAnswered`/`questionResults` from the payload, sets `answerPhaseEnded` when no time is left (frozen `timerRemainingSeconds` while locked, else `startedAt` + `timeLimitSeconds`, so auto-advance does not stall after a reload) (a reload used to show 0 answered and an empty results chart), shows game over whenever the payload carries `gameOver`, and goes to `/courses` on an ABANDONED one. Once game over is shown (`gameOverRef` latch, set by `game_over` or such a sync) any later `sync_state` without `gameOver` is ignored, so a sync built just before the game ended can't pull the screen back to results.
- `emitAdvance` sends `{from_phase, question_index}` (from render-time refs; `question_index` omitted when no question is known) and drops a repeat for the same screen within 3s (reset on `connect` and `sync_state`); the server ignores advances from a screen it already left or duplicates of one in progress, and answers them with a `sync_state`. Emits made while offline are flushed before `connect`, so the server drops them (the socket isn't registered yet). Don't revert to `emit('host_advance', {})`: ResultsPage's countdown calls `emitAdvance` inside a state updater, which StrictMode runs twice in dev.
- `question_locked`/`question_unlocked` are ignored when their `questionId` isn't the current question. `answer_status` is ignored the same way, so a late count for the previous question can't show on the next one.
- ResultsPage's `buildBars` (used for multiple_choice/true_false/multi_select) narrows the `AnswerReveal` union cleanly with no casting; only its `WordCloud` helper (fill_in_the_blank) casts through intermediate `as` types after the check instead of narrowing inline; GameOverPage casts `item.answerReveal as AnswerReveal` and then checks `'type' in reveal`. QuestionPage does not use `AnswerReveal` at all — its remaining-time calc only reads `QuestionPayload.startedAt`/`timeLimitSeconds`.
- `QuestionPayload.startedAt` is only populated on a reconnect (`sync_state`) payload — on a normal `new_question` event mid-game it's undefined, and QuestionPage's timer falls back to the flat `timeLimitSeconds` instead.
- GameOverPage and ResultsPage share the `charts/` components but each has its own `buildBars`/`optionLabel`, and they still differ: GameOverPage shows no word cloud for fill_in_the_blank, only the accepted answers as badges.
- QuestionEditorPage's `formToPayload` ends in a bare `else` that builds a `fill_in_the_blank` payload, so any type without its own branch is saved with FITB-shaped data (the T7 types have their own branches). It also computes `points_value` client-side for ACCURACY (max option points for MC/TF/FITB, sum of positive points for multi_select, both over the same non-empty rows that are sent); the backend stores whatever it is sent, and `is_correct` is judged against it. The T7 types instead send the author's Points field in both modes.
- A question type the host pages don't know degrades quietly: QuestionPage shows the raw type string, ResultsPage's `buildBars` falls through to its no-right/wrong branch (bars only if `config.options` exists, else nothing), and GameOverPage renders no distribution.
- LoginPage's OAuth2-return effect has `// eslint-disable-next-line react-hooks/exhaustive-deps` — it intentionally runs once on mount only.
- The score histogram's bucket width (`chooseWidth` in `components/charts/ScoreHistogram.tsx`, used by `buildScoreBins`) is a factor-search heuristic aiming for ~8 buckets; not obvious from the GameOverPage call site.
